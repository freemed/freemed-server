# FreeMED Go server — adversarial security & input-validation audit

Date: 2026-09-13
Base revision: `8738e1a` (master)

This is the tracked copy of the audit. The working copy lives at
`.hermes/plans/2026-09-13_security-audit.md` (`.hermes/` is gitignored — it holds agent
scratch metadata, so the report is duplicated here to keep it reviewable in the repo).

Method: static reading of every candidate sink, plus live HTTP verification against a
locally built server (`FREEMED_WEB_PORT=3999`) on the reachable MySQL/Redis. Every finding
marked VERIFIED was reproduced by me, not taken on trust.

Severity legend: CRITICAL / HIGH / MEDIUM / LOW / INFO.

---

## Executive summary

The dominant risk is not one bug — it is that **the JWT signing key ships as the literal
string `freemed`** and the four credential domains (staff, patient portal, FHIR bearer,
OAuth2 auth code) all share it. That single fact turns most other weaknesses into
end-to-end compromises: I minted an admin token offline, with no credentials, and read the
admin surface.

Second theme: **authorization is entirely self-enforced inside handlers.** The only
route-level control is `common.RequireRole("admin")` on 53 of ~325 routes; everything else
is "any authenticated user". Two patient sub-resource handlers (`dicom`, `tags`) never
check that the row belongs to the patient in the URL — reproduced end-to-end, including
a destructive delete.

Third theme: **no request-size limits and no server timeouts, combined with recursive
parsers that have no depth cap.** I proved the consequence end-to-end: a hostile DICOM SCU
that associates to the new Modality Worklist port and sends a single deeply-nested identifier (well under the payload cap) kills
the entire server process with an uncatchable `fatal error: stack overflow`. The same flaw
existed in the DICOM storage-path parser. Both are now fixed and guarded by regression tests.

Note on the MWL code specifically: it arrived with an impressive test suite (78 tests,
91 subtests, race-clean, plus a real live-MySQL end-to-end association test — all of which I
re-ran and confirmed), and it still contained a remote process-kill, because its tests only
exercised *bounded* nesting. Depth-bounded recursion on peer-supplied data is exactly the case
a happy-path suite will not cover.

## FINDINGS CONFIRMED LIVE (reproduced against my own build)

### C1 — CRITICAL · Shipped default JWT signing key → total authentication bypass (FIXED)
`config/config.go` (`defaultSessionKey`), `config.yml` (`session: key`),
(the committed key value is redacted here: it was a short, guessable dictionary word)
consumed at `cmd/freemed-server/auth.go:34`. Startup only *warned* (`config/config.go:113-115`).

I signed a staff-shaped claim set with the shipped default key — no credentials supplied —
and got:
```
GET /api/users/        HTTP=200    (admin-only)
GET /api/acl/groups    HTTP=200    (admin-only)
GET /api/tools/        HTTP=200    (admin-only)
```
**Fix (applied).** Two parts, per the agreed decision:
1. **Per-domain keys.** `config.AppConfig.DomainKey(domain)` derives a 32-byte HS256 key with
   `HMAC-SHA256(master, "freemed/jwt/v1/" + domain)`. All seven signing/verification sites now use
   it: staff (`auth.go:34`), portal (`portal_auth.go:106`), FHIR access tokens
   (`fhir_auth.go` ×3, `oauth2.go` ×2). Operators manage ONE secret; the four domain keys follow.
   A token minted for one domain can no longer verify in another.
2. **Fail-fast.** `config.AppConfig.ValidateStartup()` aborts the process (`os.Exit(1)`) when the
   key is unset, is the built-in default, or is shorter than 32 bytes. `ValidateProduction()` no
   longer warns about the key (it is fatal now). `config.yml` ships `key: ""`; `docker-compose.yml`
   and `docker-compose.prod.yml` now use `${FREEMED_SESSION_KEY:?...}` with **no default**, so a
   deploy cannot silently inherit the public placeholder. Added `.env.example`, a `make session-key`
   target that writes a generated key to a gitignored `.env`, and a `make run` target; `.env` is now
   gitignored. The auth integration test header documents the requirement.

**Verified live** (all four tokens minted from the SAME master secret):
```
legacy master-key token  -> /api/users/         401   (old shared-key scheme is dead)
staff token              -> /api/users/         200
portal token             -> /portal/auth/me     200
PORTAL token as jwt ck   -> /api/fhir/Patient/5 401   (was 200 with PHI — H2 fixed)
portal token             -> /api/patients/total 401
staff token as jwt ck    -> /api/fhir/Patient/5 200   (legitimate staff session still works)
legacy master-key token  -> /portal/auth/me     401
server with no key       -> exit 1, "FATAL: insecure configuration: session.key is not configured"
```
Unit tests: `config/config_test.go` — distinctness per domain, determinism across restarts,
master-secret sensitivity, and the four fail-fast cases.


### C2 — CRITICAL · Unbounded sequence-nesting recursion → process-killing stack overflow (two sites, both FIXED)

Decoding recurses once per sequence nesting level, and each level costs only a few
dozen bytes of input (the exact ratio is omitted here deliberately), so a crafted
object drives the recursion past the goroutine stack limit. The resulting
`fatal error: stack overflow` is a **runtime throw, not a panic** — `gin.Recovery()`
cannot catch it, so the entire FreeMED process dies. Both sites were reachable.

**Site 1 — `pkg/dicomnet/element.go` (PROVEN REMOTE, end-to-end).** A hostile SCU
associates to the MWL SCP and sends a `C-FIND-RQ` whose identifier is nested
undefined-length sequences. I proved this with a hand-built SCU against a real
in-process SCP:
```
association accepted from AE "HOSTILE", 1 presentation context(s)
sending C-FIND-RQ carrying a deeply-nested identifier (depth in the hundreds of thousands)
runtime: goroutine stack exceeds 1000000000-byte limit
fatal error: stack overflow
  github.com/freemed/freemed-server/pkg/dicomnet.decodeElementAt(...)
```
The message accumulator caps a message at 16 MiB (`MaxElementLength`), but
a body far below that cap is already enough to crash, so the cap did not help. `scp.go:498`
(`acc.DataSetBytes()`) → `handleCFind` → `element.go` `DecodeDataSet` is the sink.
The only precondition is the configured AE title, which is sent in cleartext in
every association (default `FREEMED`) and is not a secret.

**Site 2 — `pkg/dicom/parser.go:167`.** `skipUndefinedSequence` called itself with
no depth parameter. Reachable from `api/dicom.go:172` (`dicom.Parse(data)`) via
`POST /api/patient/:id/dicom`; the subagent measured the real failure on a copy at
~23M levels (184 MB), and the size is attainable because there is no body limit (M4).

**Fix (applied to both):** a `MaxSequenceDepth = 64` bound threaded through the
recursive cycle. `pkg/dicomnet` gained a depth-aware `decodeDataSetRange` /
`decodeElementAt` / `decodeSequenceItems` / `decodeUndefinedItem` chain (this also
fixed a latent hole: defined-length items re-entered the *exported* `DecodeDataSet`,
which would have reset the depth counter). `pkg/dicom` calls an internal
`skipUndefinedSequenceDepth`. Re-verified end-to-end: the same hostile SCU now
receives `malformed C-FIND identifier: ... sequence nesting exceeds 64 at <depth>`
and **the server stays alive**.

Regression tests (both fail loudly without the fix):
`TestDecodeDataSetRejectsUnboundedSequenceNesting` (crashes with `fatal error: stack
overflow` when the guard is disabled — verified by neutralizing it), `TestMaxSequenceDepthIsBounded`,
`TestSkipUndefinedSequenceDepthCap`, `TestParseDeeplyNestedSequenceTerminates`.


### H1 — HIGH · Cross-patient IDOR, read *and* destructive delete (DICOM)
`api/dicom.go:214` (`dicomGet`) and `:237` (`dicomRemove`) ignore the `:id` in
`/api/patient/:id/dicom/:itemId` entirely; the queries are `WHERE id = ?` only
(`internal/db/queries/dicom.sql`). Reproduced: a sentinel row owned by `d_patient=2`
was returned with **200** via `/api/patient/<own>/dicom/<id>` *and* via
`/api/patient/<any-other>/dicom/<id>` (a patient that does not exist), and `DELETE` through
`/api/patient/<own>/dicom/<id>` soft-deleted patient 2's study (`{"status":"deleted"}`).
Note the codebase already has the correct pattern — `api/form_results.go` checks
`row.FrPatient != patientID` and 404s. These two handlers are the outlier.
Fix: add the same ownership check (or scope the query by `d_patient`).

### H2 — HIGH · Portal token accepted as a staff FHIR session (FIXED)
`api/fhir_auth.go:63-76` — the `jwt` cookie fallback called `ValidateFHIRJWT`, which checked only
HMAC + `exp`. It never checked the token *class* (no `id` claim required), never consulted
`fhir_access_token`, and never checked revocation. Because every domain shared one key, a patient's
portal token authenticated as staff.
Reproduced before the fix: portal-shaped token as `jwt` cookie → `GET /api/fhir/Patient/5` **200**
with name, MRN and identifiers.
**Fix (applied).** The cookie branch is now a staff-session branch: new exported
`ValidateStaffSessionJWT` verifies with the **staff** domain key and additionally requires a staff-class
token (must carry `id`; must not carry `role: "patient"` or `portal: true`). Re-verified: the same
portal token now returns **401** (`signature is invalid`), while a legitimate staff cookie still
returns **200**. Also fixed the latent type-confusion panic in the same file: both branches now store
`ginjwt.MapClaims`, because gin-jwt's `ExtractClaims` bare-asserts to its own named type and
`ginjwt.MapClaims` is a *distinct defined type* from `golang-jwt`'s (so `common.GetSession`/
`RequireRole` would have panicked on any FHIR route).

### H3 — HIGH · FHIR has no scope and no patient-compartment enforcement
`api/fhir_auth.go:52-57` sets `fhir_patient_context`, but **nothing reads it** (single write,
zero readers). Handlers take the patient from the request:
`api/fhir.go:471-482` (`?patient=`), `api/fhir.go:304-317` (`PatientById`), same for
Condition / AllergyIntolerance / MedicationRequest / Immunization / Procedure / Encounter /
FamilyMemberHistory. `fhirObservationList` with no `patient` returns all patients' vitals.
No `scope` string is ever parsed. A `patient/*.read` token scoped to patient 42 can read
patient 43. Fix: enforce `fhir_patient_context` in every handler and check `scope` verbs.

### H4 — HIGH · SMART OAuth2: no user auth and no client auth
- `api/oauth2.go:25-118` `OAuth2Authorize` validates only `client_id` + exact `redirect_uri`.
  No login, no consent, and the patient context is taken **verbatim from the request**
  (`aud` query param → `InsertFhirAuthCode(PatientID: aud)`). Verified by reading.
- `api/oauth2.go:246-316` `handleClientCredentialsGrant` — the credential is **discarded**:
  `_ = clientSecretOrScope`, and there is no `client_secret` column at all
  (`internal/db/migrations/000035_smart_fhir_oauth.up.sql` has `client_id, client_name,
  redirect_uris, public_key, scopes, is_confidential, active`). Any confidential client's
  `client_id` alone mints a 1-hour token with that client's scopes.
Fix: require an authenticated staff session + consent before issuing a code; validate client
credentials for `client_credentials`; validate `aud` against the caller's access.

### H5 — HIGH · `PUT /api/preferences` is an unguarded write to the global `config` table
`api/config.go:23-28` registers `preferences` with `Authenticated:true` and **no
RequireRole**, while its sibling in the same file is guarded (`config.go:20`). The body is
written key-by-key into `config` via `UpdateConfigByOption`. The `config` table holds
`remitt_url` / `remitt_user` / `remitt_pass`, consumed by an outbound billing HTTP client
with BasicAuth. Any authenticated non-admin can reroute that integration.
Fix: `common.RequireRole("admin")` on `PUT /api/preferences`.
(Live value-leak check inconclusive: the `config` table is empty in this DB, so
`GET /api/config/all` returned `null`. Code path is unambiguous.)

### H6 — HIGH · Reachable panics (FIXED — see §1)
Three unchecked type assertions reached a panic on ordinary authenticated requests.
All three reproduced, then fixed and re-verified:
```
POST /api/patients/searchDuplicates {<string field sent as a number>} -> 500 panic patients.go:275
GET  /api/dashboard/   (JWT id claim = <non-numeric>)  -> 500  panic common/util.go:51
GET  /api/messages/view?offset=<negative>              -> 500  panic messages.go:111
GET  /api/messages/view?limit=<negative>               -> 500  panic [:-1]
GET  /api/scheduler/dailyapptrange/<from>/<to>?offset=<negative> -> 500 panic scheduler.go:112
```

## FINDINGS CONFIRMED BY CODE READING (not reproduced live)

### M1 — MEDIUM · Duplicate `common.ApiMap` key silently unregisters admin routes
`api/claim_export.go:14` and `api/claims.go:14` both assign `ApiMap["claims"]` — the only
duplicate key in the codebase (verified: `grep … | sort | uniq -d` → `claims`). `claims.go`
wins, so two admin-guarded billing routes vanish: `POST /api/claims/generate` and
`GET /api/claims/:voucher/x12`. Reproduced (once the SPA fallback was accounted for — see M3):
those two paths return the SPA HTML, not JSON.
**Caveat for the fix:** merging them naively will make gin panic — `/:id/status` and
`/:voucher/x12` are conflicting wildcard names at the same position. Rename both to a single
param name (`:id`) and update `claimX12ByVoucher`'s `c.Param("voucher")` accordingly.

### M2 — MEDIUM · Unescapable `LIKE` wildcards
User input is bound (so **not** SQL injection — I confirm the "no SQLi" conclusion), but
`%`, `_` and `\` are not escaped, so `{"ssn":"%"}` defeats the filter and a single `%` on
the unbounded paths turns into a full scan. Sites: `api/patients.go:183,188,193,198,203`;
`internal/db/queries/search.sql`; `internal/db/queries/tags.sql:42`; all 30 picklist
registry queries via `api/support.go:52`. Fix: escape before binding, or `LIKE … ESCAPE '\'`.

### M3 — MEDIUM · SPA fallback answers unknown `/api/*` with `200 + HTML`
`cmd/freemed-server/main.go:165-167` registers `m.NoRoute(...)` serving
`frontend/build/index.html` unconditionally — including for API paths. Reproduced:
```
/api/claims/generate   -> 200, text/html (SPA index)
/api/does-not-exist    -> 200, text/html (SPA index)
```
Consequences: API clients and monitors cannot distinguish "missing endpoint" from success;
it is what silently masked M1. Fix: in `NoRoute`, return a JSON 404 when the path starts
with `/api/`, `/auth`, `/oauth2`, or `/.well-known`.

### M4 — MEDIUM · No server timeouts and no body-size limit anywhere
`cmd/freemed-server/main.go:232-235` (and `:248-251` for TLS) set only `Addr` and `Handler` —
no `ReadTimeout` / `ReadHeaderTimeout` / `WriteTimeout` / `IdleTimeout` / `MaxHeaderBytes`.
No `http.MaxBytesReader` and no body-limit middleware exists anywhere. Ingest handlers call
`io.ReadAll` on the raw body or multipart file: `api/dicom.go:130`, `api/era.go:33`,
`api/ccda.go:65`, `api/eligibility.go:110`, `api/hl7.go:32,94,172`. Measured by the
subagent: a 315 MB body to `POST /api/hl7/parse` moved RSS from 30 MB to 1.71 GB; an
incomplete header set held a connection 70 s with no close.
Fix: `ReadHeaderTimeout: 10s`, `ReadTimeout: 60s`, `IdleTimeout: 120s` + a `MaxBytesReader`
limit (e.g. 32 MB) on ingest routes. This is also the enabler for C2.

### M5 — MEDIUM · Mass-deletion and cross-user reads in messaging/notifications/search
- `POST /api/messages/delete` (`api/messages.go:262-273`) — no session check, no ownership
  filter; `DeleteMessages` takes raw body IDs. Contrast `messageGet`, which does enforce
  `msg.Msgfor == session.UserId`. Mass-delete other users' secure messages.
- `GET /api/notifications/from` (`api/notifications.go:68-88`) — `NotificationsFromTimestamp`
  has no `nuser` filter, unlike the sibling `notificationsList`.
- `GET /api/search` (`api/search.go:36-52`) — `SearchMessages` has no `msgfor`/`msgby` filter.
Fix: scope all three by the session user.

### M6 — MEDIUM · Internal DB errors and schema details returned to clients
`common/response.go:20-25` `ErrorResponseFromError` sets `msg = err.Error()`. Reproduced:
`{"code":500,"message":"Error 1146 (42S02): Table 'freemed.audit_log' doesn't exist"}` and
`{"code":500,"message":"Error 1690 (22003): signed integer value is out of range in
'mysqld_stmt_execute'"}`. Leaks table names, driver internals and SQL layer to unauthenticated
reconnaissance. Panic traces also write absolute source paths into `server.log`.
Fix: log the error, return a generic message plus the request id.

### M7 — MEDIUM · Unbounded result sets (no `LIMIT`)
`ListDicomStudies` (`internal/db/queries/dicom.sql:25-33`, `GROUP BY` over the whole table)
→ `GET /api/dicom/studies`; `ListUnfiledDocs` / `ListUnreadDocs`
(`internal/db/queries/documents.sql:5,28`); `ListDicomByPatient`; `PatientSearchDuplicates`
(`internal/db/queries/patients.sql:111-119`); `ListScannedDocs`; `ListFormResultsByPatient`.
Fix: add `LIMIT` / keyset pagination.

### M8 — MEDIUM · `common/` JWT claim handling is a general panic surface
`common/util.go:51` was one instance (fixed in §1); the class is worth noting because
`Authorizator` accepts any signed token, so claim shapes are attacker-influenced whenever
the key is known (C1). `cmd/freemed-server/portal_auth.go:326` already does the correct
`switch v := patientID.(type)` — that is the pattern to standardise on.

### M9 — MEDIUM · Unauthenticated endpoints exposing more than intended
- `GET /api/metrics/` (`api/metrics.go:14-22`, `Authenticated:false`) → 200 with Prometheus
  `DefaultGatherer`: process, DB-pool and per-route metrics. (Documented as intentional in
  the project TODO; flagging that it is also useful reconnaissance.)
- `GET /api/setup/status` → `{"needs_setup":false}` — user-existence oracle.
- `POST /api/setup/initialize` → verified `409` when users exist (guard works), but the guard
  is a non-atomic `GetUserCount() == 0` check, so on a fresh install anyone who can reach the
  instance can race to create the first **admin** account. Use a DB-level lock/unique constraint.

## VERIFIED NOT VULNERABLE (negative results — no action)

- **SQL injection: none found.** I independently confirmed the subagent's conclusion. Every
  candidate where a variable reached query *text* traced to compile-time constants, `?`
  placeholders, or numeric conversion. Specifically cleared: `api/patients.go:217-231`
  (clause whitelist + bound values; the one interpolated value is `int64`), `api/support.go:50-52`
  (registry built from `TABLE_*` consts), `pkg/billing/assemble.go:545-555` (only the
  placeholder *count* is data-dependent; IDs are `int64`), `dbgen` `sqlc.slice` expansion,
  the `CALL schedulerGenerateDailySchedule` procedure (no `PREPARE`/`EXECUTE`). No dynamic
  `ORDER BY` / column / table name from any request exists.
- **XXE: not exploitable.** Only `encoding/xml`; no custom decoder, no `CharsetReader`, no
  `Strict=false`, no gokogiri/libxml anywhere. A `<!DOCTYPE … SYSTEM "file:///…">` probe errored
  out rather than resolving the entity.
- **Path traversal: none found.** The only filesystem calls are a CLI-flag CPU profile, a
  CLI-flag config path, and a `FREEMED_BACKUP_PATH`-env `os.Stat`. The DICOM `filename` is
  only written to a column.
- **No `os/exec` anywhere.**
- **No missing `rows.Close()`**, and `patientCreate` has `defer tx.Rollback()`.
- **Portal token cannot reach staff routes** (403) and **FHIR bearer tokens cannot satisfy
  the staff Authorizator** (they carry no `id` claim).
- **Fuzz negative:** 800,000 randomized inputs through `dicom.Parse`, `Parse835`, `Parse271`,
  `hl7.Unmarshal/ParseADT/ParseORU/Marshal` produced **0 panics**. All `elems[n]` accesses in
  the 835 parser are length-guarded.

## §2 RECOMMENDED ORDER OF REMEDIATION

1. **C1** — fail-fast on the default signing key, and give each credential domain its own key.
   Everything else is amplified by this.
2. **M4** — server timeouts + body limits. Cheap, and it hardens the DICOM upload path
   (**C2 site 2** was only reachable at scale because no limit exists).
3. **H1** — ownership check on the two DICOM handlers (copy `api/form_results.go`).
4. **H2/H3/H4** — FHIR/SMART token classes, patient-compartment and client authentication.
5. **H5** — `RequireRole("admin")` on `PUT /api/preferences`.
6. **M3** — JSON 404 for `/api/*` in `NoRoute`; then **M1** (merge the shadowed claims routes,
   renaming the conflicting wildcard).
7. **M5, M2, M6, M7** — scoping, wildcard escaping, error text, `LIMIT`s.

## §4 DECISIONS (agreed 2026-09-13)

| Decision | Choice |

## §6 FINDINGS DISCOVERED WHILE DELIVERING THE DICOM VIEWER (2026-09-13, later)

These were not found by the static sweeps — they were found by *exercising* the binary
delivery path end-to-end in a real browser, which nothing had done before.

### C3 — CRITICAL (pre-existing) · gzip made every raw-body response undeliverable to browsers
**Every endpoint written with `c.Data()` was broken in any browser, for any study, since gzip
was enabled.** There is no way to notice this from the server side: the handler completes, the
log shows 200, and curl without `Accept-Encoding` works fine.

Mechanism — gin sets `Content-Length` to the **uncompressed** length, and the deprecated
`github.com/gin-gonic/contrib/gzip` middleware compressed the body without clearing it:

```go
// gin v1.12 render/data.go
func (r Data) Render(w http.ResponseWriter) (err error) {
	r.WriteContentType(w)
	if len(r.Data) > 0 {
		w.Header().Set("Content-Length", strconv.Itoa(len(r.Data)))  // uncompressed length
	}
	_, err = w.Write(r.Data)
	return
}
```

Observed with `Accept-Encoding: gzip` (which every browser sends):
```
HTTP/1.1 200 OK
Content-Encoding: gzip
Content-Length: 8657        <- header
                            <- only 844 bytes actually sent
curl: (18) transfer closed with outstanding read data remaining
```
A browser honours `Content-Length` and blocks forever waiting for the other 7813 bytes. That is
exactly why the DICOM viewer sat on "Loading DICOM instance…" indefinitely — and why
`fetch()` resolved with `200` while `response.arrayBuffer()` never settled.

Affected (all 9 `c.Data()` call sites): DICOM instance retrieval ×2 (`/api/patient/:id/dicom/:itemId`
and the WADO-RS instance route), CCDA export (`/api/ccda/patient/:id/ccd`), portal CCDA,
FHIR `Patient/:id/$document`, CMS-1500 PDF, `data_store` blobs, signature images.

**Fix (applied):** replaced the deprecated middleware with an in-repo
`internal/middleware/gzip.go` that (a) drops `Content-Length` before the first compressed byte
reaches the wire so net/http falls back to chunked encoding, (b) only compresses content types
that benefit, passing `application/dicom` and `application/pdf` through untouched, and
(c) skips bodies below 512 bytes. Verified:

| request | before | after |
|---|---|---|
| DICOM + `Accept-Encoding: gzip` | `Content-Length: 8657`, 844 bytes sent, curl exit **18** | 8657 bytes, `Content-Length: 8657`, curl exit **0** (passed through uncompressed) |
| JSON + `Accept-Encoding: gzip` | `Content-Length` = uncompressed size | `Content-Encoding: gzip`, `Content-Length: 245` = actual compressed size, valid gzip |
| DICOM, no `Accept-Encoding` | correct | correct (unchanged) |

### C4 — HIGH (clinical safety) · the viewer could display the previous study's image
`frontend/src/lib/components/DicomViewer.svelte`. On teardown the component called
`loader.wadouri.fileManager.purge()`, which **resets the loader's index counter to 0**, so the next
viewer instance requested `dicomfile:0` again — the same imageId as the study just closed. The
image cache still held that entry, so cornerstone returned the **cached image of the previous
instance** and the viewer rendered it under the new study's header. Reproduced live: opening a
corrupt instance displayed the previous study's 64×64 image with its window/level.
For a medical viewer this is the worst class of bug — the wrong pixels attributed to the wrong
study. **Fix (applied):** purge the cornerstone image cache (`cornerstone.purgeCache()`) on
dispose as well. Re-verified: the corrupt instance now reports a decode error with zero non-zero
pixels, and switching back to the valid study renders 100,463 non-zero pixels / 256 luma values.

### M10 — MEDIUM (new, open) · DICOMweb QIDO/WADO are not patient-scoped
`api/dicom.go` `dicomQidoStudies` (`GET /api/dicom/studies`) and `dicomWadoRetrieve`
(`GET /api/dicom/studies/:studyUID/series/:seriesUID/instances/:sopUID`) are reachable by any
authenticated user and are **not** constrained to a patient — the study list returns every
patient's studies, and any SOP instance is retrievable by UID. This is arguably correct
DICOMweb behaviour and matches the deployment's model (authenticated staff are not
compartment-limited, as with the rest of the EMR), so it is reported rather than changed.
Decide: leave as staff-wide, or require a patient context.

### M11 — MEDIUM (new, open) · `PUT /api/claims/:id/status` has no role guard
`api/claims.go` — any authenticated user can change a claim's status. It was unguarded at base
revision `873e1a` too; preserved as-is during the route merge. Billing writes elsewhere are
admin-guarded, so this looks like an oversight. Decide whether front-desk staff legitimately
need it before adding `RequireRole("admin")`.
